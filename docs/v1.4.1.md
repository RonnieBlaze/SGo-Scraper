# v1.4.1 — Pacing listing pages

**Date:** 2026-10-31
**Previous:** [v1.4.0](v1.4.0.md)
**Status:** Current. It builds and passes `go vet` and all 18 unit tests. Live-tested on 2026-10-31: a full-profile re-run of the same model had no 500 errors, with a slightly longer wait before the first new item.

## Why

Two live runs on 2026-10-31 hit `500 Internal Server Error` on the **candids listing** pages (`offset=135` in one run; `/candids/` and `offset=63` in the next). Each time the retry succeeded on the second attempt and all 154 candid posts were found, so nothing was lost. No other page type has returned a 500.

A 500 comes from the site's server, not from the scraper's request. The likely cause is that a long candids listing is slow for the server to build and sometimes times out. That's an informed guess, since the server can't be inspected from here. The scraper made it worse by loading listing pages back-to-back with no pause. Since v1.4.0 skips finished items instantly, it went straight from the photosets listing into a burst of candids listing pages.

## Changed

| Change | Detail | Files |
|--------|--------|-------|
| Pause before every listing page | `pauseBeforeListingPage` waits `DOWNLOAD_DELAY_MS` (default 2 s) before each `?offset=` page of the photosets, candids, videos and blog listings, including the first page of each section | `crawler.go` (`getAllLinks`) |
| Pause before group-thread comment pages | These were also fetched back-to-back | `crawler.go` (`getAllGroupThreadImageBuckets`) |
| Retry success is shown | When a retried request succeeds, a green line follows the yellow retry line: `[retry ok] <url> — succeeded on attempt 2` | `http.go` (`withRetry`) |

**Cost:** about 2 seconds per listing page. A full profile with a few pages per section takes roughly 10–20 seconds longer.
- **Single album, post or video URLs:** no listing pages are loaded, so no extra wait.
- **Re-running an existing model:** the wait is most noticeable, because skipped items are instant and the listing pauses are most of the run time.
- **A new model:** the same pauses happen, but they're small next to the delays between the downloads themselves.

**Limits:** this can make the 500s less frequent, but it can't stop them, because they come from the server. The retry still covers any that happen.

## Tests added

- `TestGetAllLinks`: follows `?offset=` pages, removes duplicate links, and keeps the links already found when a later page fails (recording that failure).
